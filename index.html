A VPN for networks that block VPNs

Veilway is open-source software for running your own VPN server on a censored or hostile network, for yourself or a small group. The current release, v0.3.10-alpha, installs a server and its web panel with one script or Docker, and connects from Linux, macOS, Windows and Android.

AlphaIt has had no outside security review. Every transport is rated Detectable. The macOS and Windows apps are compiled and tested on CI only, and have never connected to a node on a real machine. Expect bugs, and tell us about them.

What it does differently

The tunnel stays standard. The work goes into getting it through, and into one set of tools from the server to the phone.

  • WireGuard's own cryptography

    The tunnel is unchanged WireGuard, through boringtun. Veilway works around the tunnel and does not invent its own encryption.

  • Transports for where UDP is blocked

    The tunnel can travel over obfuscated UDP, TLS, WebSocket or a fronted HTTP path. Someone who probes the server without an account gets the ordinary answer of the operator's own website. All of them are rated Detectable.

  • One engine for the server and the apps

    The server and the apps are built on the same Rust core, which is also a library for anyone who wants a WireGuard engine in their own program. Subscription requests are encrypted end to end, and the apps ask before they use a backup update address.

  • Enter one server, leave from another

    Two servers can be linked, so users connect to one and their traffic leaves from the other. The operators pair them with two codes and compare a fingerprint, in the panel or on the command line. One panel can also run several servers, with one subscription and one quota across them.

  • English and Persian from the start

    The design system and the docs are written in both, with right-to-left layout, Persian digits and Jalali dates, and so is every app built on them.

Install a server

One script installs the node, the panel or both on a Linux server, and checks every download's signature with minisign before it installs anything. Run it as root:

curl -fsSL https://raw.githubusercontent.com/veilway-project/veilway/main/scripts/veilway.sh | sudo bash

The same script, saved as veilway.sh, also installs a relay mirror (install mirror), a relay (install relay), adds the Xray add-on (addon xray install) and moves the panel's admin pages to a new path (panel-prefix).

Docker images with a compose file are another option: ghcr.io/veilway-project/veilway and ghcr.io/veilway-project/veilway-panel. The getting started guide walks through both.

Where it stands

Do not rely on Veilway where a failure would put you at risk. Every transport is rated Detectable: a censor that looks closely can tell it from ordinary traffic. Nothing in it has been tested against deep packet inspection or active probing, and its protocol spec is a draft only the project has reviewed.

Works today
  • A server that runs WireGuard for many users over five transports: plain UDP, obfuscated UDP, TLS, WebSocket and a fronted HTTP path. The client speaks HTTP/2 like Chrome on TLS, WebSocket and fronted, and the node offers it when you turn on http2. WebSocket and fronted run behind your own web server, and the panel has presets for the shapes of the fronted path. It has routing rules, quotas, and config reload without a restart. Someone who probes it without an account gets the operator's own website.
  • A web panel in English and Persian: admin sign-in with a password and a one-time code, users, devices and groups, subscription links and QR codes, inbounds, exits (a default and one per user), routing, guided setup for an entry node and a reverse tunnel, relays, traffic history, DNS and logs, notices to every device, more than one admin, backup and restore, an update button, and an admin API with tokens. It listens on loopback only, and your web server in front of it provides TLS.
  • Subscriptions that stay private on the way: requests and answers are encrypted end to end (Oblivious HTTP keys over HPKE), so a relay mirror sees nothing of them. A link carries the server's gateway key. Named endpoints sit at sub_path/<name> and can be assigned per user and per group. Static and relay mirrors serve as backup update addresses, and an app asks before it uses one. A subscription can also travel as a password-protected .vwsealed file.
  • Desktop apps for Linux, macOS and Windows, in English and Persian. They import a subscription by link, file or QR picture, ask plainly before anything risky, connect with one button, and show live speed, usage, the exit and the connection details. Share subscription passes on the link only, never the device's keys. A kill switch blocks traffic when the tunnel fails, and the app updates itself.
  • An Android app (arm64) on the same engine, with the same screens in both languages and its own updater. It cannot scan a QR code with the camera yet.
  • Links between two servers, paired with codes both operators compare. A node can forward a TCP or UDP port through a link, with limits per source. Relays can be set per user and per group.
  • Offline bundles: one signed file with app updates, subscription documents and notices, made with veilway bundle make and checked with veilway bundle inspect. The desktop and Android apps show what is in it, and nothing applies without a tap.
  • An optional Xray add-on, off by default: the node runs the official Xray release as a child process, so stock apps can connect with VLESS and Trojan over TLS or with Shadowsocks, over TCP and UDP. Their traffic counts in the same quotas and follows the same rules. Veilway is a separate project, and the add-on does not replace Xray.
  • Xray links in the desktop app on Linux, macOS and Windows (vless, vmess, trojan and ss). The add-on is installed on request from a pinned release, and these profiles show "TCP and UDP only".
  • Borrowed-site mode, an alpha feature that is off by default: a connection that does not prove itself is relayed to a real website byte for byte. The panel sets it up, and the apps use it only after "Alpha transports" is turned on. Only the project has reviewed it, and it is rated Detectable.

Not built yet

The Android app does not connect to Xray links yet, and the server add-on has no VMess, no Reality and no l3 or chain exits. Split tunneling and store builds are planned for a later release. HTTP/2 and the fronted shapes have not run behind a real CDN.
